# GraphKV 相关子图读取与安全备用路径：研究原型

日期：2026-10-07。版本：research-0.1。

**建议研究这个版本。现有实验支持先缩小问题的读取范围，再判断图缓存是否还有独立价值。** 本包把这个想法实现为可检查的推理原型和对照 notebook。它没有修改原 v5，没有更改 RoPE、节点传播公式或模型权重，也没有在本研究端取得新的 Tulu3 模型成绩。

## 一、为什么是这三个部分

你提交的实验已经提供了较清楚的方向：

| 已有证据 | 这个版本的回应 |
|---|---|
| LYRA 只读 source 5＋target 2 时答银；加 source 4 后答铜 | 在问题到来后，只读相关目标与必要来源 |
| FP32 中，v5 与完整图参考生成一致，全图 LYRA 仍错 | 首版继续使用已核对的缓存计算，先研究读取策略 |
| 修改已编码目标的边，旧缓存不变，原 validate 仍通过 | 缓存建好后冻结图；更新时新建快照，旧计划拒绝执行 |
| 普通顺序在此前小型对照中明显更稳定 | 提供普通顺序备用路径，并保留同证据对照 |
| 修正标记分词边界后，匹配条件的生成 tokens 未变 | 不继续把这个标记作为当前主要修复手段 |

这没有证明“source 4 对所有问题都是坏信息”，也没有定位唯一的注意力头或内部原因。它支持一个更有限、更实用的判断：**当前模型在全图读取时容易把无关事实带入关系回答，控制读取范围值得优先验证。**

论文在节点编码时利用图关系，但回答阶段让问题与生成 token 读取来源和目标的表示。因此，“建缓存时用了图”不等于“回答时只读取相关关系”。新版本显式增加后一层选择。[Graph-KV 论文 v2](https://arxiv.org/abs/2506.07334v2)

## 二、使用方式

1. 把整个压缩包解压到 Linux 上的一个新目录。
2. 在该目录打开 `GraphKV_相关子图与安全备用路径.ipynb`，使用已安装 v5 依赖的 Jupyter 内核。
3. 重启内核，从上到下运行。首格默认仓库 `/home/lyh/hcy_work/GraphKV_refactor_v5`、模型 `/home/lyh/hcy_work/GraphKV/models/Tulu3-Block-FT`、物理 GPU 3；可以修改。
4. 先执行小型 CPU 集成测试，通过后才加载你的 BF16 模型。原型固定 Transformers 4.50.0、Llama、eager 注意力、单个 CPU 或单张 GPU。
5. 结果写入本包下新的 `results/时间戳/`，每条回答后保存 JSON。完成后保留 JSON 与运行后的 notebook。

只需一张卡运行当前小实验。首版没有验证模型跨四张卡切分；另三张卡可留给其他独立实验。不会重新下载模型，也不会覆盖 v5 模块。

默认运行原图四路对照、固定缓存形状诊断、备用路径检查、8 个独立 pilot 图。CPU FP32 复核默认关闭；有足够内存并愿意等待时，在首格设置 `RUN_CPU_FP32=True`。

## 三、系统实际如何决定路径

```text
输入问题
   │
   ├─ 明确命中实体别名，且未触发保守回退规则
   │      → 找到目标节点
   │      → 补齐图中必要来源
   │      → 检查版本与预算
   │      → 使用选中节点的 GraphKV 缓存回答
   │
   └─ 无明确命中、别名冲突、检测到比较/否定/广范围表达
          → 全部候选原文
          → 检查版本与预算
          → 普通顺序重新编码并回答

版本不一致 → 报错并停止
预算不足   → 返回 budget_exceeded，不截断证据、不生成答案
```

以现有小图为例：

| 问题 | 选中来源 | 选中目标 |
|---|---|---|
| ORION 用什么材料？ | 4 | 1 |
| LYRA 用什么材料？ | 5 | 2 |
| NOVA 合用哪两种材料？ | 4、5 | 3 |
| BETA 供应什么材料？ | 5 | 无 |

不能只保留目标节点：已有实验表明，目标缓存并不能稳定替代原始材料事实。多个必要来源也不能为满足固定 top-k 被任意删掉。

**这里的选择器是明确名称匹配基线。** 英文别名检查完整词边界并忽略大小写，中文别名使用子串匹配。它不会理解所有指代、否定、隐含关系、拼写变体和混合实体问题。广范围规则是有限的保守词表，不是完整的语义风险检测器；例如某些复杂问题仍可能命中名称并走图路径。结果必须用于发现这些漏检。

别名是节点的公开元数据。实验的正确答案与正确证据标签只传给评分函数，从不传给选择器。合成图上名称显式、边正确，因此选择难度很低，不能把这里的证据召回成绩包装成真实 RAG 检索能力。

### 备用路径能保证什么

它提供的是一种已在此前小实验中较稳定的读取方式。它**不能保证事实正确，也不会自动知道图答案是否错误**。当前系统在生成前选择路径，不根据“模型很自信”决定是否重试。

当前未知/歧义问题缺乏可信的小范围选择，因此备用路径读取全部候选。未来有独立验证过的候选检索器后，可以改成“候选小子图顺序重算”，但不能通过把不确定的候选裁得更小来掩盖召回损失。

缓存损坏、计划过期或模型发生更新会直接报错。这样的工程错误需要重建快照，不能吞掉异常后宣称备用成功。

## 四、缓存保护的范围

本版采用**静态快照**，刻意不实现复杂的动态局部更新。

- 已编码目标的依赖不能通过 `set_edges()` 改变；批量改边先检查，失败不会留下部分修改。
- 完整缓存封存后，新增来源、传播目标、替换前缀和改边均被拒绝；即便内容相同的重新设置也不允许。
- 图、节点与元数据字典变为只读映射。
- 查询前后检查布局、缓存 tensor 身份与原地修改计数；常规原地修改或 tensor 替换会被发现。
- 查询计划包含图内容版本和独立快照编号；新快照不能接收旧计划。
- 检查模型参数、缓冲区、配置与运行模式的变化，以及 tokenizer 常用身份信息和实际输入 tokens。
- notebook 额外核对所有原始 KV 字节的摘要，确认查询未污染可复用节点。

正常使用时，改正文、边、模型参数或分词方式，应重新创建 `QueryEngine`。首版会重建整个静态图，而非声称已经实现局部失效传播。

这不是防恶意篡改的安全隔离。通过 `.data` 绕过 tensor 计数、任意更改 tokenizer 内部实现、替换模型方法或并发修改状态，都不在保证范围。不要在多线程里共享可变模型与本引擎。实际模型文件路径是来源记录，不等于整个权重文件的密码学身份认证。

查询输入长度和逻辑位置均计入预算，预留完整生成上限。超预算时明确返回失败；不会静默删除第二条必要来源。构建时也检查单个传播输入和逻辑范围，但这不是显存容量预测器；大型图库的缓存存储与搬运需要后续专门设计。

## 五、四个对照怎样区分收益来源

| 条件 | 文本范围 | 读取方式 | 回答的问题 |
|---|---|---|---|
| graph_all | 全部节点 | v5 图缓存 | 原全图表现 |
| graph_selected | 实际选择器选出的节点 | 同一批已建好的图缓存 | 控制读取范围是否改善 |
| sequential_selected | 与上一项完全相同 | 原文按普通顺序重新编码 | 改善是否主要来自选择证据 |
| sequential_all | 全部节点 | 普通顺序 | 当前模型的完整输入基线 |

所有条件沿用相同 prefix、问题模板、各块 token IDs、贪心解码与输出上限。普通顺序路径把同样的 token 块串接起来，而非额外改写提示词。图路径保留全图预先规划的逻辑位置，不随着子图变短而重新安排位置。

`hybrid` 是规划器真实选择路径的入口。对现有明确实体问题，它与 `graph_selected` 相同；对未知和广范围问题，notebook 单独验证其普通顺序分支。

未在这个小包里重复加入独立分块、所有位置变体和训练对照；它们属于后续机制扩展。此前研究资料仍应保留，不能把本包四路对照当成全部消融实验。

## 六、固定形状干预为什么必要

前次删除 source 4 时，同时缩短了物理缓存。本包增加更严格的诊断：全部五节点 KV 保持不变，只改变问题和生成 token 能读取哪些区间。

| 条件 | 可见节点 | 重点 |
|---|---|---|
| A | 4、5、1、2、3 | 与原全图生成对齐 |
| B | 5、2 | 相关证据 |
| C | 4、5、2 | 只比 B 多看 source 4 |
| D | 5、1、2、3 | 去掉直接读取 source 4 的通道 |

屏蔽施加于问题预填充和每一步生成，保留 prefix 及合法的历史问题/输出可见性。遮住的原始 KV 区间不会在下一步重新开放。

若 B 答银、C 答铜，读取可见性解释得到更直接支持。若翻转消失，应重新检查之前删块时的长度、布局和低精度数值影响。先核对 A 与原适配器；若其 BF16 完整输出不同，暂不作强机制结论，用 FP32 补核。

D 中的 target 1/3 已含 source 4 传播的信息，因此只移除了直接读取 source 4 的通道，并未彻底清除“铜”。固定形状屏蔽是诊断，仍计算完整缓存，不能据此宣称节省显存或加速。

## 七、需要怎样的结果，才值得继续

| 观察到的结果 | 建议 |
|---|---|
| 相关子图图模式和顺序模式都明显变好 | 先确认选择证据的收益，不把全部提升归于 GraphKV |
| 相关子图图模式仍较差，顺序模式稳定 | 实际系统优先顺序重算；研究端再做注意力校准、局部重算或适配训练 |
| 手工正确证据有效，实际选择器经常漏证据 | 优先改检索与关系补齐，暂不动底层缓存 |
| 图与顺序质量接近，在重复查询/组合复用中图模式总成本更低 | 有继续做缓存存储、复制和调度优化的明确理由 |
| 只在 LYRA 恢复，独立图无稳定改善 | 视为个例修复，不宣称普遍有效 |
| 材料词对了，但关系或引用仍错 | 不能判为完整质量提升 |

默认 8 图只是流程试跑。后续可用 30 个开发图固定策略、100 个保留图评估；数量是启动预算，不是统计充分性的保证。每个图有多个关联问题，误差区间应按图分组，而非将全部问答视为独立样本。

更重要的是逐步加难：名字改写和指代、多个主体、缺边/错边、过密的邻居、长文档、更多无关材料、多跳关系、证据不足。当前原型只支持一跳 source→target，不能直接用于宣称多跳能力。

论文 RAG 中的来源边还可能来自检索排名，而非你的人工精确事实关系。因此，选择目标后补齐所有邻居在真实数据中可能仍带入大量无关信息；最终需要问题相关的邻居筛选与证据覆盖评估。[论文 RAG 设置](https://arxiv.org/abs/2506.07334v2)

### 性能暂不下结论

日志保存建缓存和生成耗时，但它们不是完整性能基准。普通顺序路径目前每次重新编码，尚未加入固定序列的可复用前缀缓存；图模式也尚未分解复制、搬运和逐 token 生成成本。不要直接把两列时间相除称为加速倍数。

下一阶段应给普通顺序基线同等的缓存复用机会，再分别测首次使用、同图多问、不同组合和更新后的总成本。质量不过关时，低在线延迟本身不构成优势。

## 八、代码与验证状态

| 文件 | 用途 |
|---|---|
| `graphkv_safe/policy.py` | 不依赖 torch 的图描述与查询规划 |
| `graphkv_safe/guard.py` | 缓存生命周期保护 |
| `graphkv_safe/runtime.py` | 调用原 v5 编码，执行图/顺序/固定形状诊断 |

| `GraphKV_相关子图与安全备用路径.ipynb` | 用户模型上的完整运行入口 |
| `LOCAL_TEST_REPORT.txt` | 本研究端实际执行记录 |
| `MANIFEST.sha256` | 包内文件摘要 |

本研究端只实际执行不依赖 torch 的测试和语法检查。张量集成测试及 Tulu3 推理需要在用户环境中运行，不能把“已编写测试”称为“已验证模型效果”。Notebook 首先运行集成测试，任何失败或跳过都会阻止继续实验。

集成测试涵盖：与原 v5 缓存字节/输出数值对齐、全可见 mask 对齐、固定形状子集与实际删块的 FP32 对齐、顺序缓存生成与每步重算对齐、原始 KV 不变、旧计划拒绝、参数/缓存修改拒绝、预算超限不调用模型。

上游依据：[Graph-COM/GraphKV](https://github.com/Graph-COM/GraphKV)、[用户 v5](https://github.com/zmsnhcy/GraphKV_refactor_v5)。编码装配逻辑沿用 v5；本包是外围研究扩展，不能被视为作者原版实现或经过正式验证的新论文结果。

**对论文价值的判断仍应区分两层：**“按结构构建和复用缓存”值得研究；“这样建好的缓存能让现有模型稳定完成关系推理”需要实际证据。本版的目的，就是让两者可以分别评估，避免为了保留 GraphKV 而牺牲答案质量。
